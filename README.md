# 猿通讯聊天记录查看器（fast-ytx-chatlog-viewer）

基于 **Electron + React + TypeScript** 的 Windows 桌面应用，用于解析并展示
**猿通讯（YuanTX）** 客户端 SQLite 数据库中的聊天记录。应用**只读**打开源库，
解码后建立本地索引缓存，面向十万级消息提供流畅的浏览、多维检索与消息右键复制体验。

## 数据源与编码说明

### 数据来源

待解析的聊天记录来自 **猿通讯（YuanTX）** 客户端。删除消息、导出或备份后得到的是
SQLite 数据库文件（如 `message3763.db`），本应用直接读取该文件，**不做任何写入**。

### 源库结构

样例库（`message3763.db`，约 94 MB，78,614 条消息 / 211 个会话）包含三张表：

- `chat_list`：会话列表（`id` / `name` / `avatar` / `type` / `lastMessage` / `seq` …）
- `message_list`：消息主表（`id` / `name` / `chatId` / `fromId` / `type` / `at` /
  `content` / `timestamp` / `mine` / `withDraw` / `strDate` / `messageType` …）
- `chat_top`：置顶会话

### content 编码规则

`content` 存在两种形态，实践中均需处理：

1. **明文**，如 `好的`
2. **字节数组编码**，如 `encode229,165,189,231,154,132`
   → 去掉 `encode` 前缀，按逗号拆分为十进制字节，按 **UTF-8** 解码 → `好的`

此外大量字段存放字面量 `undefined` / `null` 脏值，读取时统一归一化为空。

### messageType 归一化

| 原始值 | 归一化类型 | 说明 |
| --- | --- | --- |
| `0` / `5` | `text` | 纯文本 |
| `1` | `file` | 文件消息，content 为 `<a class="file-wrapper">` 富文本 |
| `2` | `image` | 图片消息，content 为 `<img class="chat-img">` |
| `3` | `emoji` | 表情 / 富文本（非 HTML 时按 `text` 兜底） |
| `4` | `at` | @提醒（非 HTML 时按 `text` 兜底） |
| `6` | `quote` | 引用回复（`chat-quote`） |
| `8` | `system` | 群系统消息（入群 / 退群等） |
| `withDraw='true'` | `withdrawn` | 已撤回 |
| `null` / `'undefined'` / 其他 | 结构启发式判定，兜底 `text` | 历史消息 |

## 技术架构

```
渲染进程 (React + Tailwind + zustand + @tanstack/react-virtual)
        │  window.api（contextBridge 白名单）
预加载 (preload, contextIsolation + sandbox)
        │  IPC（通道常量 + 入参校验）
主进程
  ├─ 数据源发现（程序目录 / resources / userData）
  ├─ 源库只读连接（better-sqlite3，readonly）
  ├─ 内容解码器（encode → UTF-8、脏值归一化、HTML → 纯文本）
  └─ 索引缓存（userData/index-cache，流式构建 + 明文与分面索引）
```

### 为何使用索引缓存

源库 `content` 为字节编码，SQL 层无法直接做明文匹配，且每条记录都需要解码。
因此首次加载时**流式扫描**只读源库，将解码后的明文与分面字段写入 `userData`
下的缓存库（按「源文件路径 + 大小 + 修改时间」哈希命名），后续启动直接复用；
源库指纹变化时自动重建，界面所有查询都走缓存，兼顾准确性与查询性能。

**不写入源库**：源库始终以 `readonly: true` 打开。

### 性能与内存策略

- 分页使用 **keyset 游标**（`timestamp + row_id` 复合条件），避免大偏移 `OFFSET` 性能坍塌
- 渲染层全程**虚拟滚动**，DOM 节点数量恒定，内存不随数据量线性膨胀
- 缓存连接限制 `cache_size`，消息内容按需解码，原始内容仅在有富文本时下发

**启动不被磁盘拖死**（面向 GB 级数据库设计）：

- 数据源发现只做**廉价探测**（读取 `sqlite_master` 判断表结构），不做任何全表扫描
- `COUNT(*)` / `MAX(timestamp)` 这类昂贵统计**不在启动路径上**，改为惰性计算并持久化到
  `userData/source-stats.json`，后续启动直接命中；面板中可通过「统计全部来源」按需触发
- 主进程**先把窗口显示出来**，再开始扫描与建索引，避免出现「长时间无窗口」
- 发现结果带短时缓存，避免一次启动被重复扫描多遍
- 界面提供启动遮罩与实时进度（当前文件、已解析条数、进度条）

**索引构建是增量的**，分三级复用（越靠前越省）：

| 场景 | 行为 |
| --- | --- |
| 源库集合与各文件大小/修改时间均未变化 | 直接复用缓存，**不做任何构建**（0 ms） |
| 某个源库只是追加了新消息 | **行级增量**：只解码 `rowid > 水位` 的新行，通常几十毫秒 |
| 源库发生删除 / 撤回 / 被 VACUUM 重写 | **整库重解析**该文件（校验不通过时的安全兜底） |
| 新增文件 | 只解析新增文件 |
| 更高优先级源库消息数减少（发生删除） | 自动补解码被其覆盖的旧备份，保证并集语义不丢数据 |
| 折叠模式下全量库消息减少 | 自动改用「合并历史快照」并持久化，避免历史被静默丢掉 |

**行级增量的正确性校验**：只有源库当前内容恰好等于「上次解析的集合 ∪ `rowid > 水位` 的新行」
时才只追加，判定用四个数同时成立来保证：

| 比对项 | 拦截的异常 |
| --- | --- |
| `COUNT(*)` | 中间有行被删除（SQLite 只在删除「最大 rowid」时才可能补洞，删中间行会留下永久空洞） |
| `SUM(rowid)` / `MAX(rowid)` | rowid 不再从水位连续增长，或文件被 VACUUM 重写 |
| 已撤回条数 | 旧消息被撤回（行数不变，但内容已被改写） |
| **水位锚点消息 id** | 删掉最大 rowid 那一行后新行复用了同一个 rowid —— 此时行数与 rowid 之和恰好还原，只有比对「水位那一行的消息 id」才能发现该行已被替换 |

任一不成立即回退为整库重解析，因此只是「损失一点速度」，不会丢数据。
若源库是 `WITHOUT ROWID` 表、或 `rowid` 被同名列遮蔽，则自动始终走整库重解析。

实测（3 个样例库，合计 235,022 行）：

| 场景 | 改造前 | 按源增量 |
| --- | --- | --- |
| 冷启动（首次完整解析） | — | 约 **11.1 s**，界面 **1.8 s** 即出现并显示进度 |
| 二次启动（无任何变化） | 每次重扫全表，分钟级 | **约 2.3 s 可用**，索引构建 **0 ms** |
| 改动 1 个文件后启动 | 全量重解码 约 11.4 s | **约 3.4 s**（只解析 1 个库） |

在此基础上再加**快照链折叠**与**行级增量**，样例目录（1 个全量库 + 3 个历史快照）的解码量
从 313,647 行降到 **78,625 行**（约 4 倍）；实测追加 3 条新消息时构建耗时 **358 ms**，
而同一份库整库重解析需要 **3,278 ms**（约 9 倍）。若目录里还存在同名同大小的副本
（例如 `release/win-unpacked/message3763.db`），会按「字节数 + 修改时间」判重后一并折叠。

查询侧：时间线单页约 **10–25 ms**，全局检索约 **50–110 ms**（关键字命中规模 12 ~ 2,962 条）。

## 开发与构建

### 环境要求

- Node.js 20+（开发机实测 Node 24）
- npm 10+
- Windows 10/11（打包目标平台）

### 安装依赖

本项目使用原生模块 `better-sqlite3`，需针对 **Electron 的 ABI** 构建，而系统 Node 版本
通常没有对应预编译包。项目内 `.npmrc` 已设置 `ignore-scripts=true`，因此：

```bash
npm install     # 只拉取依赖，不执行安装脚本
npm run setup   # 下载 Electron 运行时 + 安装 better-sqlite3 的 Electron 预编译二进制
```

> 若网络受限，可先设置镜像：
> `$env:ELECTRON_MIRROR='https://npmmirror.com/mirrors/electron/'`
> 再执行 `npm run setup`。

### 开发运行

```bash
npm run dev        # 开发模式（热更新）
npm run typecheck  # TypeScript 全量类型检查
npm run build      # 构建到 out/
```

开发模式下「程序目录」即为项目根目录，因此把 `*.db` 放在项目根目录即可被自动发现。

### 校验快照链（可选，离线分析）

想确认手上这批文件是否满足「历史快照 ⊆ 最新全量库」，可运行：

```bash
# better-sqlite3 按 Electron 的 ABI 编译，需借用 Electron 自带的 Node
$env:ELECTRON_RUN_AS_NODE=1; npx electron scripts/verify-snapshot-chain.mjs "D:\Projects\fast-ytx-chatlog-viewer"
```

脚本会按链输出每个文件的行数 / 最新消息时间 / 大小，逐条比对全量库是否为各快照的超集，
并给出「只解析全量库能省下多少解码量」以及 `message_list` 的列结构与 rowid 可用性。

### 打包 Windows 产物

```bash
npm run build:win
```

产物输出到 `release/`：

- `ChatLogViewer-1.0.0-x64-setup.exe` —— NSIS 安装包（可选安装目录、创建桌面与开始菜单快捷方式）
- `ChatLogViewer-1.0.0-x64-portable.exe` —— 免安装绿色版

> **关于 winCodeSign**：写入 exe 图标与版本信息依赖 electron-builder 的 winCodeSign 工具包。
> 该 7z 包内的 `darwin/10.12/lib/*.dylib` 是 macOS 符号链接，在没有管理员权限且未开启
> 「开发者模式」的 Windows 上解压会失败（`CreateSymbolicLink: 客户端没有所需的特权`）。
> 因此 `build:win` 会先执行 `scripts/prepare-wincodesign.mjs`：自行下载并**排除 darwin 目录**
> 解压到 `%LOCALAPPDATA%\electron-builder\Cache\winCodeSign\winCodeSign-2.6.0`（已存在则跳过）。
> 网络受限时可先设置镜像：
> `$env:ELECTRON_BUILDER_BINARIES_MIRROR='https://npmmirror.com/mirrors/electron-builder-binaries/'`

也可单独执行：

```bash
npm run prepare:wincodesign
```

## 数据源发现与配置

### 选择范围：单文件 vs 目录

数据源面板把来源分成两类，选择方式即对应两种查看模式：

| 选择 | 含义 |
| --- | --- |
| **按目录** | 收集该目录下**最新全量库**作为整体查看（默认；历史快照自动折叠） |
| 单个文件 | 只查看该 `.db` 的内容 |

#### 快照链：为什么目录选择默认只解析一个库

猿通讯**每次退出时会把整库另存为一份带时间戳的副本**：

```
message3763.db                     ← 最新全量库（应用运行期间一直在追加）
message3763-2026-09-04-17-50-52.db ← 历史快照（不会再被修改）
message3763-2026-09-10-09-57-57.db
message3763-2026-09-14-10-14-37.db
```

快照的内容**整体包含于**全量库（实测行数 78,039 → 78,369 → 78,614 → 78,625，单调递增），
所以目录选择时默认做「快照链折叠」：

1. 按**文件名**把 `message3763` 与 `message3763-<时间戳>` 归为**同一条链**；
2. 链上存在无时间戳的全量库 → 只解析它，其余快照整体折叠跳过；
3. 链上只有快照（手工删过全量库）→ 只解析时间最新的一份；
4. 不同基名（`message3761` 与 `message3763`）永远是两条独立的链，不会被合并；
5. 跨目录出现「基名相同且字节数与修改时间完全一致」的文件（例如 `release/win-unpacked`
   里的那份副本）→ 判为同一份拷贝，只解析其中一份。

被折叠的快照仍会列在数据源面板里（标注「已折叠」），可以单独选中查看。
面板中的「合并历史快照」开关可关闭折叠，回到逐库合并去重的行为。

#### 合并模式（开启开关后）

需要把不同来源（不同机器 / 不同时间的导出）合在一起看时，会按下面的规则合并：

1. 按**优先级顺序**依次读取源库：用户配置来源优先 → 库内数据最新（已统计时按
   `MAX(timestamp)`，否则退回文件修改时间/大小）→ 约定文件名 → 猿通讯目录 → 文件修改时间
2. 以**消息 `id`** 为唯一键去重，**保留优先级更高（更新）的那一份**
3. 会话的 `message_count` / `last_timestamp` 在**合并去重之后**重新统计，因此展示的是
   "全部数据库按 ID 去重后的总量"，不会重复计数
4. 存在消息但已从会话列表移除的会话会被自动补齐（单聊取对方昵称、群聊以 ID 尾号标记），
   避免这部分消息不可见
5. 构建是**增量**的：仅重新解析新增、内容变化或数据不完整的源库，其余复用缓存中的行
   （详见「性能与内存策略」）。若更高优先级源库的消息数**减少**（发生删除），会自动补解码
   被其覆盖的旧备份，保持"所有库并集"的语义

面板与状态栏会显示当前范围、参与解析的库数、折叠的快照数与去重条数，便于核对。

### 扫描来源

应用按以下优先级收集候选数据库（去重）：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | **用户添加的单个文件** | 面板中「添加文件」选择的任意 `.db`（可位于任何位置） |
| 2 | **用户添加的目录** | 面板中「添加目录」选择的目录，会**递归**扫描子目录（最多 3 层） |
| 3 | **猿通讯默认目录** | `%APPDATA%\boctx`（`C:\Users\<用户名>\AppData\Roaming\boctx`），猿通讯聊天记录的默认存放位置 |
| 4 | 程序目录 | 开发态为项目根目录；打包态为 exe 同目录、`resources` 及其上级 |
| 5 | userData | `%APPDATA%\ChatLogViewer` |
| 6 | 环境变量 | `CHATLOG_DATA_DIR`，多个目录用分号分隔，便于便携分发 |

其他规则：

- 只收集 `*.db`，且必须同时包含 `message_list` 与 `chat_list` 表才视为可用
- 递归扫描会跳过 `node_modules`、`File`、`Cache`、`index-cache`、隐藏目录等无关目录，
  单次最多收集 200 个文件，避免拖慢启动
- 排序（同时也是合并优先级）：用户添加的来源优先 → 库内数据最新 → 约定文件名
  （`message*.db`，即无时间戳的全量库）→ 猿通讯目录 → 文件修改时间
- **下次启动会恢复上次使用的范围**（记录在 `config.json`），无需重复选择；首次使用则
  默认取「数据最新那个库所在目录」作为范围
- 配置持久化在 `%APPDATA%\ChatLogViewer\config.json`，可手工编辑：

  ```json
  {
    "dataDirs": [],
    "dataFiles": [],
    "lastSelection": { "kind": "dir", "path": "D:\\chatlog" },
    "mergeSnapshots": false
  }
  ```

  `mergeSnapshots` 即面板中的「合并历史快照」开关；检测到全量库消息减少（发生删除）时，
  应用会自动把它置为 `true` 并在界面上提示，以免历史消息被静默丢掉。

在「数据源」面板中可以：添加文件 / 添加目录、移除已添加来源、重新扫描，选择按目录合并
或单个文件，并查看内置默认目录列表（猿通讯默认目录带绿色标记）。清单中每个条目会标注
**已添加**、**猿通讯默认路径**、**使用中** 等状态，文件条目还会显示消息条数与最新数据时间。

> 安装版安装在 `Program Files` 时该目录只读，此时请把数据库放到 `userData`，
> 或在面板中用「添加文件」直接指定；绿色版可直接把 `*.db` 放在程序同级目录。

## 安全说明

- `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`
- 渲染层仅能通过 `contextBridge` 暴露的白名单通道访问能力
- 主进程对全部 IPC 入参做类型与范围校验（字符串长度、枚举白名单、数组上限、日期格式）
- 渲染层**不使用** `dangerouslySetInnerHTML`，富文本一律解析为结构化数据后由 React 组件渲染
- 通过 CSP 限制资源来源；外链一律交由系统浏览器打开，禁止窗口内导航与新窗口
- 源数据库**零写入**：均为只读连接；缓存写入仅发生在 `userData/index-cache`
